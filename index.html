Marketplace front-end

OzCar

One of the biggest used-car marketplaces in its market: search, vehicle pages with finance calculators, live video presentations and an online auction dashboard.

Client
Car marketplace and dealer group
Where
Australia
Role
Front-end, from Adobe XD to production
Stack
HTML, SCSS, JavaScript, jQuery, Bootstrap

The problem

A dealer group with a large, fast-moving inventory needed a public site that sells cars and an auction panel that dealers work in all day. The designs arrived as Adobe XD files; every screen had to become production markup that a back-end team could wire up without redrawing anything.

What I did

  • Built the full public front-end: make and model search with dependent filters, the vehicle page with its finance calculator and live video presentation request, and the reviews and dealer pages.
  • Built the auction side as a separate application shell: a left navigation of filters (make, model, series, year, variant, kilometres) driving a dashboard of upcoming auctions.
  • Kept the markup semantic and the components reusable so the same card, filter and form patterns repeat across both sides of the product.

Technical notes

  • Hand-written SCSS with a small component layer over the Bootstrap grid
  • Progressive enhancement: filters and calculators work as plain forms first, then jQuery adds the live behaviour
  • Sprite and image discipline for an inventory site that shows dozens of photos per page

Result

  • Shipped across the marketplace, vehicle and auction screens.
  • The public site is currently limited to visitors in Australia after a wave of attacks on it, so the visuals here are the screens as they were built.

Multi-tenant CMS

Devlo CMS ديفلو

One Laravel application, one deploy, twenty-four Arabic news sites, each with its own theme, modules, languages and editorial team.

Client
Newsroom platform running 24 sites
Where
Türkiye, Palestine, Yemen
Role
Design and full-stack, product owner of the front-end
Stack
Laravel, Livewire, MySQL, Redis, Alpine

The problem

Newsrooms were being built one at a time, each a fork of the last. A fix in one site never reached the others, and every new client meant weeks of duplicated work. The platform had to run many sites from one codebase without any site seeing another's features, permissions or content.

What I did

  • Designed the editorial interface and the theming model, then built both: 456 Livewire components and 839 Blade views behind one admin panel that works in Arabic, English and Turkish, right-to-left throughout.
  • Put tenancy on 113 feature flags, so nothing reaches a site that did not ask for it, and mirrored 40 permission modules across four actions with a command that re-syncs them.
  • Wrote the guards: 50 artisan commands, six of which exist only to fail when something invisible breaks, such as a feature leaking between tenants, a route permission that exists nowhere else, or a translation key that renders in Arabic because the fallback locale is Arabic.

Technical notes

  • 66 models and 247 migrations under one schema, tenant-scoped at the query layer
  • 5,874 translation keys, checked in CI so a missing English string fails the build instead of shipping
  • Share-card pipeline that regenerates Open Graph images per article, after a favicon and a WebP had turned shared links into bare blue lines on WhatsApp

Result

  • Powers Quds News Network, Tayaqan, Maktoob Media, Hodhod, Adeni Cast and the Saleh Al-Arouri archive, among others.
  • Full write-up in the case studies on my GitHub profile, including the ideas that were measured and thrown away.

High-traffic newsroom

Quds News Network قدس الإخبارية

A high-volume Arabic newsroom publishing all day. Real Chrome users load it inside Google's FAST band.

Client
Palestinian news network
Where
Palestine
Role
Design and full-stack, on Devlo CMS
Stack
Laravel, Livewire, RTL

The problem

A newsroom that publishes around the clock, in Arabic, to an audience that is overwhelmingly on phones and often on poor connections. The front page changes every few minutes and has to stay fast while carrying video, podcasts, live tickers and a dark mode.

What I did

  • Designed the reading experience for right-to-left first: the grid, the type scale and the density were set on real Arabic headlines, not on Latin placeholder text.
  • Built the front page on Devlo modules: breaking strip, lead story, headline rail, audio briefing, podcast and translation sections, each switchable by the editors.
  • Ran the performance pass described in the newsroom audit case study: fonts cut from 749 KB to 78 KB, a preload that was hurting removed, and the Cloudflare rule that explained a TTFB nobody could move.

Technical notes

  • Server-rendered Blade with Livewire only where the page actually changes
  • Article schema, share images and hreflang generated per story
  • Measured weekly against Google's PageSpeed API from my GitHub profile

Result

  • Field data from real Chrome users over 28 days: FAST, with LCP at 2.33 s and INP at 104 ms.
  • Lab scores on 20 September 2026: 99 on desktop, 82 on mobile, with accessibility and SEO at 100 on both.

Data platform

Mo3ta معطي

A data platform rather than a website: dashboards, an interactive map and charts over a large Arabic dataset, rendered on the server so the numbers are indexable.

Client
Palestine information centre
Where
Palestine
Role
Design and full-stack
Stack
Laravel, Inertia, Vue 3, SSR, Charts

The problem

Statistics about Palestine were scattered across PDFs and spreadsheets. The centre wanted one place where a journalist, a researcher or a student could find a number, see it in context on a map or a chart, and cite it. The page had to be readable by search engines, which rules out a client-only dashboard.

What I did

  • Designed the visual language for numbers in Arabic: a mono scale for figures, a restrained palette so the map and the charts carry the colour, and a right-to-left layout that keeps axes and legends readable.
  • Built the platform on Laravel with Inertia and Vue 3, server-side rendered, so every indicator page arrives as real HTML and the interactivity layers on top.
  • Built the map and chart components as one reusable set fed from the same indicator model, with export and share per figure.

Technical notes

  • Inertia SSR for indexable first paint, Vue 3 for the interactive layer
  • Indicator model with sources and dates on every figure, so a number is never shown without where it came from
  • Dashboards, maps and charts share tokens with the marketing pages, so the product and the site read as one system

Result

  • Live at mo3ta.ps with the indicator library, map and dashboards in production.

Fact-checking platform

Musnad مسند

Arabic fact-checking: every claim carries its verdict on the card. Scores 100 in all four Lighthouse categories on desktop, re-measured weekly.

Client
News and claim verification
Where
Yemen
Role
Design and full-stack
Stack
Laravel, Livewire, Schema, SEO

The problem

A fact-checking team needed a site where the verdict is the first thing a reader sees, in Arabic, on a phone, and where each investigation can be found by the claim people are actually searching for. Speed and trust signals mattered more than decoration.

What I did

  • Designed the verdict system: a fixed set of labels (fabricated, misleading, old, true) with one colour each, shown on every card and every article header before anything else.
  • Built the platform on Laravel and Livewire with the reading page tuned for long Arabic text: type scale, line length and the placement of sources.
  • Wrote a technical SEO and AI-search audit of the live site, 20 findings ranked by impact, and turned it into the fix plan for the next release.

Technical notes

  • Server-rendered pages with Livewire pagination kept crawlable
  • Organization, Article and ClaimReview structured data on the roadmap from the audit
  • Weekly PageSpeed measurement with the raw JSON kept in the open

Result

  • Desktop: 100 for performance, accessibility, best practices and SEO on 20 September 2026.
  • Mobile performance dropped to 78 in the same run. It stays on this page until the fix ships, because a table that only shows the good weeks is a screenshot with extra steps.

How a project runs.

The same six steps whether it is a landing page or a platform. Written, staged, and measured before it is called done.

  1. 01

    Brief

    A written brief and my questions back. Goals and content before layout, in writing, so decisions stay documented for your team.

  2. 02

    Structure

    Flows, page list and what each screen must do. For Arabic products this is where right-to-left is decided, not patched in later.

  3. 03

    First screen

    One screen designed and agreed before the rest exists. If the direction is wrong it costs a day, not a project.

  4. 04

    Build

    Hand-written, delivered in reviewable stages. Design and code come from the same person, so nothing is lost in a handover.

  5. 05

    Measure

    PageSpeed on both devices, accessibility checks, and a pass at 375 px before anything is called finished.

  6. 06

    Keep it running

    Most of my work lands in systems that already run. I read the existing code before I change it, and keep what works.
